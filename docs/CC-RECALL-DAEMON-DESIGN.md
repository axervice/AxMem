# Claude Code 召回低延迟方案 3：常驻本地服务 + HTTP hook（设计稿）

## 1. 结论、边界与准入条件

**推荐：同一 Windows 用户登录时启动一个常驻召回服务，三个召回事件优先直接使用 `type: "http"`；宿主故障语义未验证前，不把纯 HTTP 接线交给日常会话。** 不安装系统级服务、不申请管理员权限、不为每个 Claude Code 会话启动一个服务。用户不接受登录自启时，可选 SessionStart 按需启动，但必须明确其启动事件不能承诺 0.2 秒。

固定产品规则不变：**动态召回最多 3 条、仅提醒、绝不新增拦截；召回故障时动作继续，并在当前会话显示一行可见提示**。正常零匹配、不支持的动作、已送达重放不是故障。现有其他 hook 的权限决定不由召回服务覆盖：这里的“不拦截”不是强行允许原本被用户权限规则拒绝的动作。

### 1.1 事实与证据边界

- 任务提供的实测基线：2026-11-16，真实记忆 772 条，N=10 中位数；prompt 端到端 0.76s，编辑／命令前 0.77–0.80s；单独 bash+node 启动 0.17s，词法索引装载约 0.35s，记忆读取 0.03s，require 0.03s。各分项不能直接相加冒充端到端测量。逐次 spawn 的端到端下限约 0.3s。
- 任务提供的宿主文档事实只有：存在 `type: "http"`，hook JSON 输入作为 POST body，`Content-Type: application/json`，响应 body 沿用 command hook 的 JSON 输出格式。
- **哪些事件支持 HTTP、自定义 header 是否支持、拒绝连接／超时／非 2xx 时宿主怎么处理，全部待测**。本文不虚构可直接粘贴安装的宿主配置字段。
- 本稿已阅读树内 `hook.cjs`、memory-source、recall-selector、recall-topic-index、recall-source-proof、recall-receipt、recall-health、merge-hooks 及阶段 1 文档；以实现而非历史文档中的过期描述为依据。
- 当前工具可见的 `adapters/claude-code/` 没有 `trial-install.cjs`，相应目录与 docs 搜索也无引用。因此“三条精确身份、可逐字节回滚”作为**任务给定的阶段 1 安装契约**使用，不声称已审查该工具。实施前由负责人补齐或确认基线；不能用会接入 8 条 hook 的 `merge-hooks.cjs` 顶替。
- 任务给定 worktree／分支／提交只作为背景，没有运行 git 复核。本文是设计，不是部署记录、实测达标报告或修改代码的授权。

### 1.2 三道准入门

| 准入门 | 通过条件 | 失败行为 |
|---|---|---|
| 故障安全 | 三事件在服务拒连、超时、断连、非 2xx、坏响应下均继续动作，且有一行真正用户可见、可抑制重复的告警 | 使用第 3 节 command 桥安全模式；若宿主连 command 输出也不展示，则停止日常试装，不把日志当可见提示 |
| 安全边界 | loopback、凭证权限、凭证传递、端口冒充风险及同用户信任边界均已确认 | 不开放未认证端口，不用 URL token 偷渡；留在安全桥或原阶段 1 |
| 性能 | 真实宿主逐事件端到端中位数 ≤0.2s，统计同时披露故障率、冷启动和并发长尾 | 标记未达标；不得用纯 HTTP 服务内部耗时、空响应或减少召回成功率冒充达标 |

理由：只把 Node 留在后台仍可能每次重载索引；只改 HTTP 也不能替已经死亡的服务生成告警。性能、可见故障与安全必须分别有证据，不能靠一个“daemon 已启动”状态包办。

## 2. 谁启动、何时启动与跨会话单实例

### 2.1 三种启动方法

| 方法 | 做法与环境变化 | 成本／选择理由 | 失败行为 |
|---|---|---|---|
| SessionStart command 按需启动 | 每次 SessionStart 运行轻量启动器；先查本用户服务身份，再在缺失时争用单实例锁并启动。无需登录任务，但增加一个 command 路径 | 环境改动较少；每个新会话／resume／compact 仍可能付 spawn 下限约 0.3s。不能假定同事件 command 先于 HTTP，也不能靠两个并列 hook 保证启动顺序 | 启动器自己处理该次 SessionStart 的转发或降级，不同时另挂一个会竞速的 HTTP SessionStart；不等待完整建索引。其他事件服务未就绪按第 3 节降级 |
| **本用户登录自启（推荐）** | 经 Jax 明确同意后登记一个本用户、非提权的 Windows 登录计划任务；启动稳定安装路径中的 Node 和服务。三个事件都可走 HTTP | 多会话共摊一次 require／索引预热，SessionStart 也不需逐次 spawn；最符合“每个事件 ≤0.2s”。代价是登录任务、后台进程／worker、内存常驻、一个本地端口与私有运行目录 | 登录任务失败、服务崩溃、机器刚登录未预热时不能等用户动作；走已验证宿主告警或安全桥。不自动提权、不关闭防火墙 |
| 手动启动 | 用户明确启动／停止，不登记登录任务 | 环境最少，适合隔离实验；依赖记忆，不适合大量并发会话长期使用 | 漏启动不静默当零匹配；提示并继续。未满足故障准入时不能只留下直连 HTTP hook |

默认不设“最后一个会话退出就关服务”：宿主 SessionEnd、崩溃和其他代理的退出不能可靠做引用计数，贸然关机会影响仍在工作的会话。服务在用户注销或显式卸载时退出；闲置内存占用与是否采用后续闲置策略由实测决定。登录自启只启动已授权安装的版本，不跟随工作树正在编辑的代码热更新。

### 2.2 单实例与端口争用

- 实例范围为**本机 + 当前 OS 用户 SID**，不按 Claude 会话、repo 或工作树建实例。一个实例固定一份已批准的 memory/state 配置；第二份冲突配置请求报 `profile-conflict`，不得覆盖全局服务配置或切换别的会话的来源。
- 使用带当前 SID 访问控制的 Windows 命名互斥量，覆盖同用户不同登录会话；实施时验证其命名空间与权限，不把普通 Node PID 文件当互斥量。若跨登录会话互斥不可用，由固定私有运行目录的独占锁配合独占监听兜底，必须补竞争测试，不能静默产生两实例。
- 安装时选择一个空闲高位端口并固定在该安装代中；只监听 `127.0.0.1`，独占绑定，不启用复用端口。启动时获取互斥量，再绑定、预热、发布 ready 描述。运行描述仅含安装 ID、协议版本、端口、PID、进程起始身份、generation 和 ready 状态；凭证单独保存。
- 竞争失败者只连接并认证已有的同安装、同协议实例；不能凭“端口有响应”或 PID 存在就认为是 AxMem。端口被陌生进程占用时，不杀对方、不自动修改全局 settings 去追新端口，记录冲突并降级。PID 复用、权限拒绝均不能成为杀进程依据。
- 推荐一个轻量常驻前端与可替换查询 worker：前端负责认证、限流、期限和告警；worker 持有一代完整 corpus／词法索引。worker 崩溃前端可回 200 降级；前端自身崩溃仍需第 3 节宿主／桥兜底。后台重启采用 1s、5s、30s 退避，5 分钟内最多 3 次，之后等待显式修复／下次登录，不让每个会话同时重启。
- 安装代版本失配时旧服务只提供兼容的无记忆降级响应，不动态加载新代码。升级由同一事务停旧、起新；失败恢复旧代。普通 hook 请求没有启动程序、任意读文件或关闭服务的权限。

## 3. HTTP 事件路径、崩溃兜底与不刷屏

### 3.1 正常事件协议

三个逻辑 hook 仍为 SessionStart、UserPromptSubmit、PreToolUse（matcher 保持 `Edit|Write|MultiEdit|Bash`）。主路径为：

> 宿主 POST 原始 hook JSON → 本地认证／限额 → 按 session/actor 排队 → 验证源版本 → 常驻 worker 查询 → 既有预算与回执准备 → 源最终复核 → 一次 JSON 响应 → 传输结果结算。

不增加 PostToolUse、Stop 或写后闸接线，不改其他插件。SessionStart 仍按原 epoch、健康与 Kernel 唯一发送者规则处理；动态召回最多 3 条，不把 Kernel 改造成全量记忆注入。未知事件不伪造 `hookEventName`，仅输出安全的顶层状态。

服务能响应时，内部召回错误统一返回 **HTTP 200 + 合法非拦截 JSON**，首次告警使用顶层 `systemMessage`：`AxMem 召回暂不可用；工作继续。` 不把内部错误返回 500 交给未知的宿主错误路径；不输出 deny、block、停止处理字段，也不主动覆盖其他权限规则。用户可见告警只用这一个渠道；additionalContext 不再复制同一句故障行，日志保留无敏感信息的错误码。200 空结果 body 应选宿主实测接受的空对象或空正文，不假定 command 的空 stdout 可以直接照搬；不选未验证的 204 语义。

前端设计处理预算 120ms（含读取有界请求、队列、查询、准备与输出开销），同 key 排队预算不超过 20ms；宿主 HTTP 超时拟设 200ms，单位、最小值与支持性待测。超时前无结果就回降级，不等重建、不在前台重试。Node 的同步磁盘 I/O 与事件循环暂停不是硬实时取消，必须实测预算溢出；不能把计时器当绝对保证。worker 迟到结果不得补发第二段 JSON、覆盖已结算任务或制造 emitted。

请求体上限沿用 256KiB、prompt 上限 64KiB，工具输入沿用已有校验。鉴权失败、非法来源、超限等协议／安全错误可返回无记忆内容的 401／403／413／429；这些状态在宿主中的继续与告警行为也必须纳入故障矩阵，不能仅测试业务错误的 200。

### 3.2 服务死掉后谁负责提示

| 方案 | 能保证什么／原因 | 代价、失败行为与结论 |
|---|---|---|
| 直接 HTTP，依赖宿主 | 不付每事件 spawn；只有宿主能在目标进程死亡后接住连接失败 | **仅在实测证明“继续 + 可见一行 + 不刷屏”后作为默认快路径**。若宿主静默丢弃、弹阻断错误或每次刷错误，即不合格；服务内部 try/catch 无法补救 |
| **极轻 command 桥（安全后备）** | 每事件只启动桥、读输入／私有凭证、向常驻服务转发；拒连、超时、坏 JSON、非 2xx 均捕获，输出一行 systemMessage 后退出 0；不加载 corpus／索引 | 是完整替换该逻辑 hook 的传输入口，不与直连 HTTP 并列、不重复召回。即使只有轻量客户端，已知 spawn 下限仍约 0.3s，预计 0.30–0.48s，不能称 ≤0.2s 方案。stdout／宿主本身故障仍需实测，不能保证任意系统损坏都能显示 |
| HTTP 指向常驻轻量前端／本地代理 | worker 崩溃时前端仍能回 200 告警，减少实际拒连次数 | 前端也会死，OS 重启／登录竞态也存在。“有 watchdog”不等于必定可用；不单独满足硬保证。更可靠的 OS 组件还增加部署面，依旧需要宿主兜底 |
| HTTP 旁边加 command 健康探针 | 可发现部分不可用 | 不推荐：每事件仍有 spawn；探针成功后服务也可能死亡；hook 顺序、输出合并均未知，可能双告警、双召回，不能声称无成本保险 |

**上线决策明确而非自动猜测**：负责人先测宿主。符合故障门槛的版本安装三条 HTTP；否则安装三条安全桥并标注“故障安全，但延迟目标未达成”，或继续阶段 1。不能等拒连后再由 HTTP 服务自动把自己切换为 command，也不能在某会话内偷偷修改全局 settings。没有已知宿主能力能同时兑现两项要求时，就如实报告阻塞问题。

### 3.3 告警状态机与可见性

- “一行”按**每个会话的一次连续故障事件段**解释：第一次失败显示；同段其余失败仅累计计数，不每个工具调用再刷。不同会话各自至少看到一次，不用一个全局布尔值让其他窗口静默。持续故障在下一次请求且距离上次提示 ≥5 分钟时可再提示一行；不设向终端主动写字的后台线程。
- 只有一次完整成功召回查询才解除该故障段；单纯 `/health` 可达、没有执行召回、或中性不支持动作不冒充恢复。频繁成功／失败抖动另设每会话 60 秒告警冷却，计数不丢。恢复不另刷成功行，SessionStart 可显示汇总健康。
- 告警节流是新传输层状态，按 session 为主、actor 做诊断；原候选／seen 仍严格按 session+actor。安全桥的节流文件在私有运行目录中用短事务原子更新，不与 recall-receipt 的锁混用；服务与桥共用同一告警键，切模式时不全屏重发。
- 缺 session 时不建立共享 unknown 桶；不可靠归属的调用无法同时保证“每会话第一行”和严格节流，应记录身份缺失并暂停推广。节流存储不可写时，宁可当前调用仍给一行也不静默；极端持续磁盘故障可能重复提示，这是待修故障，不宣称保证防刷屏。
- **直连 HTTP 拒连时服务不能参与节流**。宿主是否有合适的可见提示与按会话去重机制待测；只有“自动显示每次错误”也不算通过。若不能满足，切安全桥。不能把 additionalContext（只给模型）、后台日志或回执当作用户已经看见。
- 所有 hook 被宿主禁用、整个客户端挂起、输出通道损坏时，hook 无法报告自己没有被调用；安装验收必须检查真实 UI，此类边界不承诺虚假的必达。

## 4. 数据新鲜度、重建与半成品隔离

### 4.1 检测策略

**每请求前后元数据复核是正确性主线，文件监听只是提速，定期全量 hash 补漏。** 来源仅采用 `memory-source.cjs` 的固定七文件集合，包含可选 classes／archive 文件的出现与消失，不由 POST 指定任意路径。

1. generation 持有根目录身份、每个文件的 dev／ino／size／mtime／ctime、内容 SHA-256、解析器／索引版本、`snapshotId` 和完整 corpus。每次请求入场和响应前调用现有 `sourcesUnchanged`；不每次从 JSON 磁盘缓存恢复 MiniSearch。
2. watcher 在启动后持续观察目录的修改、重命名、删除和重建，约 50ms 合并重复通知；通知立即使 generation 进入“待复核”，不在 watcher 回调里做全量同步建索引。watcher 抛错／漏事件不阻断请求侧 stat 检查。
3. 独立后台每 30 秒做一次不信任旧解析缓存的字节 hash 校验；修改了时间戳但大小未变的内容也能被发现。每次重建采用新一代缓存命名空间或无缓存读取，避免“已发现 hash 改变却又读回同 stamp 的旧缓存”。休眠恢复立即安排校验。
4. 常规文件写入在下一次请求的元数据检查即可发现；元数据完全伪装的变动只承诺在后台 hash 周期加读取／调度时间后发现，**不承诺瞬时发现**。若用户要求防恶意同用户篡改而非普通编辑的新鲜度，需要每请求读 hash 或更强隔离，延迟与权限另评估。

### 4.2 构建与发布

- 前端持有 `activeGeneration` 句柄。B worker 在独立执行环境中读取、解析、构建并保留**活的** MiniSearch／terms 对象；A worker 不原地修改任何 corpus、Map、Set 或索引。Object.freeze 不能单独冻结 Map／Set 内容，发布后只读由接口所有权与测试保证。
- B 完成完整源读取、边界证明、索引预热和最终源版本复核后才报告 ready。前端再核对 generation 版本和来源，单次替换 active 句柄；请求从入场至输出始终持有同一代引用。不要把已建索引序列化回前端再在每个请求里 loadJS。
- 已入场请求如最终复核发现来源变化，丢弃正文并降级，不标 emitted；新请求一旦知道 A 已脏，就不继续发 A 的旧记忆。**默认宁可本次无召回并提示，也不把已删除／已 supersede 的规则继续推给用户。** A 可保留给尚未完成的引用或故障诊断，但不是已知过期时的服务策略。
- 源未变、仅主动预热或实现版本升级时，可继续使用经复核的完整 A；B 构建失败不影响仍有效的 A。源已变且 B 失败，则保持不可用，退避重建，不回退到已知过期 A。
- 引用归零后释放旧 worker 的内存。通常最多“活动 A + 构建 B”两代；连续保存时取消过时构建、合并到最新源版本，不无限累积 worker。达到内存／队列上限时先放弃构建或当前召回并降级，不拖死宿主。

请求**不会等待全量重建**；只有有限的元数据检查与队列等待。构建 CPU、读盘与 GC 仍会争夺机器资源，所谓“不阻塞”指不在前端同步执行构建，不代表没有竞争开销。空缓存冷启动也走同样过程，在 ready 前快速返回一行降级，而不是卡住第一个 prompt 等 0.35 秒装索引。

保证的是“任何请求只读完整、版本绑定的一代，永不读半建索引”。普通文件系统并不提供七个文件跨文件事务；读前后 stamp/hash 检查可拒绝观察到的变化，但无法证明用户连续编辑的多个文件属于一个原子提交。最终复核之后到传输之间的极小窗口也不等于宿主执行时最新状态；这与既有快照语义一致，不做更强宣传。

## 5. 本地端口、token 与威胁边界

### 5.1 存放与传递

- 新建的安装专属私有运行根拟为 `%LOCALAPPDATA%/AxMem/cc-recall/<installation-id>/`，其中 `token` 文件存放由密码学安全随机源生成的至少 256 位 bearer 凭证（文件靠 ACL 保护，不声称已加密）；运行描述、告警节流和无正文诊断分开。此路径仅是设计，本文没有访问或创建它。
- Windows 使用显式 DACL：当前用户和必要的 SYSTEM 维护身份可访问，移除普通其他用户／Users／Everyone 的读取继承，目录与文件都检查。只写 `mode: 0600` 不能当 Windows ACL 保证；若以后支持 POSIX，目录 0700、文件 0600。拒绝 reparse point／symlink 指向和不安全父目录，权限校验失败就不启用 HTTP。
- 首选宿主允许的认证 header，例如 Authorization bearer；**是否支持 header，以及是否支持从受限文件或环境引用取值，待测**。不把进程环境必然传给宿主、动态文件展开或变量插值当既有能力。
- 若只支持 header 字面量：安装器必须把凭证副本写进全局 settings 的本 hook 字段。因此 token 不再“只存在私有文件”，settings、备份、安装日志中的副本都属于秘密；先验证并征得同意限制其 ACL，不得为了本功能让其他工具失去它们需要的访问。备份亦受保护，日志只显示指纹，不显示值。
- 若不支持自定义 header，也没有经过验证的等价安全凭证机制：**不把 token 塞进 URL path/query，不改写宿主原始事件 body，不开放免认证端口**。改用 command 桥读取私有文件再发送 header，或只经受当前 SID 保护的本地 IPC 连接。接受因此未达延迟目标，等待宿主能力补齐。URL 会进入错误文本、调试日志、配置与截图，不作为默认退路。
- token 在安装／升级代之间轮换；换代须将服务凭证与本安装 hook 作为事务更新。旧客户端可能保留旧设置，兼容窗口只对已登记旧代、限定时长开放；进入卸载立即撤销旧 token 的记忆访问权限，完整停机时作废全部权限。若因旧接线尚在而保留临时降级响应器，它只能回固定告警，不再持有／返回任何记忆。不能每次重启随机换值却不更新宿主。token 永不进入命令行、进程标题、普通日志或回执。

### 5.2 端点与输入防护

只监听 IPv4 `127.0.0.1`，不是 `0.0.0.0`、LAN 地址或模糊的 localhost 双栈绑定。不自动开放防火墙、不外连、不转发重定向。端点限于已认证的事件 POST 和不含正文的健康信息；管理／关闭接口使用更严格的私有控制通道，而非普通 recall token。

先验证认证、Host 目标与请求类型，再处理有界 JSON；凭证比较采用恒时比较。拒绝浏览器跨站 Origin，不设置允许跨域的 CORS，不提供 GET 搜索／全文导出／任意路径读取。prompt、command、正文仅瞬时用于召回，不记入 access log；错误响应不带文件路径或内部堆栈。按连接、用户服务总量和 session 队列限额，抵御本地滥发请求；未认证者得不到条目数、tag、命中差异或记忆正文。有效请求也最多返回产品规定的 3 条，但“最多 3 条”不是对有 token 攻击者的防枚举保障。

### 5.3 不能用 loopback 夸大的保证

- token + ACL 阻挡的是**没有凭证的本地进程和其他普通用户对真实服务的读取**。同一 OS 用户下的恶意进程往往能读取 settings／token／原始记忆，甚至读进程内存；管理员也可绕过。这一方案不能把同一用户下的 Claude、其他代理和恶意程序变成安全沙箱。session_id／agent_id 是关联信息，不是身份认证凭证。
- 若 Jax 的要求包括“同一 Windows 账号下的其他代理也绝对读不到记忆”，本方案安全边界不够：需要独立 OS 身份／受限代理能力或沙箱，不能靠多加一个 header 实现。确认前不宣称已满足该更强要求。
- **端口冒充另算**：服务活着时独占绑定防抢占；服务死后，另一个本地进程仍可能抢占端口，裸 HTTP 的宿主会先把 token 和事件 POST 给假服务。随机端口、PID 文件都不能证明服务器身份。若恶意本地进程属于威胁模型，直连 HTTP 还需要经实测的服务端身份认证方案（例如宿主支持并校验证书的本地 HTTPS，证书信任部署须另行批准），否则禁用直连，安全桥采用带 SID ACL 的命名管道，并在发送凭证／事件前验证服务端进程的 SID 与登记实例身份；仅给管道取一个固定名字仍不算服务端认证。不要用“校验 token”声称已经防住假服务器。
- 服务崩溃后的残余监听、错误凭证、ACL 拒绝一律进入第 3 节故障路径，不能为了恢复召回临时改成免认证。停用／回收前先撤销凭证；回收站是可恢复保管，不是秘密销毁，含旧凭证的备份必须保持权限且凭证已失效。

## 6. 并发、会话隔离与既有回执语义

### 6.1 只共享不可变来源，不共享会话状态

直接复用 `core/recall-receipt.cjs`：

- `identity(input, invocationId)` 仍以 hostname、session_id、agent_id 生成 key；无 session 使用 invocationId，不落共享 nosess 桶。无 actor 按原实现标 null，禁止跨调用复用任务候选；不能猜子代理是谁。
- `actionId` 继续依赖 session、actor、tool_use_id、工具和规范化输入；没有 tool_use_id 不用输入 hash 猜“同一动作”。同文本的再次尝试可以是不同动作。
- 每个 key 设有界 FIFO；同 key 的 epoch／taskId／candidates／seen／receipt 事务串行，锁覆盖 prepared、传输结果结算及 save/close。不同 key 可交错查询、独立计数；同一 active corpus 只读共享。服务前端排队顺序仅是接收顺序，不伪造宿主没有提供的因果顺序。
- SessionStart 仍增加 epoch 并清候选与 seen；prompt 建新 task 并重置本任务候选；prompt 送达不能压掉 PreToolUse；相同动作／规则版本重放才可抑制，新动作或规则新版可再次提醒。
- HTTP 服务与旧 command／Post 兼容 hook 可能共用状态文件，仍用 `openStore` 原有磁盘锁与原子写入；不能因 daemon 内已有队列就删除跨进程锁或另写“常驻版 receipt”。

外部锁竞争沿用原 `skipBusy` 的只读已提交快照行为，不写 seen／marker／健康，不把 busy 当索引故障。前端另记无正文的 `accounting=read-only-busy` 诊断，不能把未落盘调用计成完整持久化账。既有 30 秒租约／claim 回收窗口和“持久写拒绝加残留锁可能静默 busy”的已知限制仍存在；本设计不声称重写或顺带修复它们。正常事务远小于租约，过长任务必须终止并释放，不以扩大 TTL 代替验证。

同一 session 的多个缺 actor 请求可能共用 null actor 状态，这是现有身份契约的限制：候选禁用能减少误用，但不能创造不存在的隔离身份。负责人必须测主会话、子代理和其他会话的实际 ID；若多 actor 无法区分，不把缓存命中作为跨 actor 继承，推广前明确能力降级。

### 6.2 传输改变不等于宿主确认送达

沿用 received → source-ready → selected → prepared → emitted → completed／degraded 的语义，来源 hash、条目整条／omitted、action marker 和 `hostConfirmed: unknown` 保持不变。整条超预算仍不裁掉例外后冒充完整正文。

HTTP 不是 stdout：新 transport 层需要把“本地 HTTP 响应完整写入”映射到最低限度 emitted；`stdout_result` 保持 `not-attempted`，另用经兼容测试允许的 HTTP transport 诊断字段记录 written／failed 和 body hash。不能在未测消费者兼容前随意换 schema，也不能把 HTTP 200 或 socket 接受当“用户／模型读过”。`recall-receipt` 的身份、store、action marker、Post suppression 函数本身不需要重写；接线层与回执组装需适配。

直连宿主 HTTP 时，prepared 与状态预检在响应之前；只有整条 body 写入回调完成、没有已知 abort／错误时才记 emitted、更新 seen 和 Pre marker。客户端提前断开、只有 prepared、worker 迟到均不标送达。body 写出后补记失败仍存在不可原子化窗口：不能追发第二个 JSON，只记诊断并在后续事件显示一次故障摘要。不主动重试已可能送达的请求，不承诺 exactly-once。

command 桥不是宿主本身：**服务把 body 发给桥，不能就当作已向宿主输出**。桥的私有协议需增加两阶段传输结算：服务返回 prepared 的 payload、delivery ID 与 hash；桥只将 payload 写到 stdout，成功后经已认证私有通道确认本地写入，服务才记 emitted／seen／marker，并记录 `stdout_result=written`。确认不代表 hostConfirmed。确认失败、桥被杀或 stdout 失败时保留 prepared／未确认，不抑制之后的召回；宁可可能重复提醒，也不误记已送达。事务锁／队列只有短且有上限的确认租约（拟 200ms，实测调整且必须远小于既有 30s 锁租约），超期释放，迟到确认不修改后继任务。桥的确认发送设很短上限（拟 10ms）并计入 command 端到端耗时，不等待服务的完整落盘回复；未能确认就保留未知，不能让宿主一直等账本。不得因持久化失败让桥退出非零或再发一份正文。直连宿主无此私有确认协议，不能要求未文档化的宿主 ACK。

旧 `suppressPost` 仍核对同 action、marker 和源文件 hash，只有完整 Pre 的证据才能抑制旧 Post；不把所有会话共享的缓存命中当作某会话已收到。健康继续调用 `recordInvocation`／`checkHealth`，每次有多个错误也只计一次失败；daemon 活着不等于最近成功召回。

队列满、请求 deadline 或 worker 崩溃时，对当前请求尽快回降级并继续动作，不能挤占其他 session 无限等待。新前端必须保证每个请求恰好一次结算入口；取消后的后台结果不得再改候选或计一次成功。缺失持久回执时如实记“持久计数未知”。

## 7. 试装、一步卸载与逐字节回滚

### 7.1 扩展阶段 1 工具，而非另做全局安装器

以下入口名是**拟议接口，不是当前可执行命令**：在任务所述 `adapters/claude-code/trial-install.cjs` 增加 daemon 试装模式、预览模式和 `--undo <installation-id>`。先确认缺失的阶段 1 基线，再复用它的原始字节备份、身份追踪、冲突检测、原子替换和恢复引擎；HTTP 类型与服务资产管理属于新增代码。

仍只拥有三个逻辑召回身份：SessionStart、UserPromptSubmit、匹配四工具的 PreToolUse。HTTP 模式不额外挂 command 探针；安全桥模式用三个 command 替换它们；按需启动模式由 SessionStart 的同一入口兼任启动。安装清单在私有目录保存 event、matcher、type、完整传输配置指纹、位置、安装代与预期数量；header/token 值不出现在普通日志。不能靠 command／URL 含有 axmem 子串就删除别人条目。

已有阶段 1 三条只有在其身份与基线备份均可证明归属时才能迁移，保存旧条目的精确字节和位置。未知相似 hook、重复精确身份、其他插件条目一律先报冲突，不悄悄合并。不得调用 merge-hooks 的全量 WANT，把原有五条写后纪律 hook 顺带安装或卸载。

### 7.2 全局 settings 的事务与多会话影响

1. 先预览三个 hook、后台任务、稳定程序目录、端口、token 副本／ACL 的变化，取得 Jax 同意；先在隔离假 HOME/settings/memory/state 验证。真实安装另行批准，本文不执行。
2. 安装事务保存 settings 的原始字节及 pre-hash（含 BOM、CRLF、空白、原文件不存在状态），保存原 ACL、计划 post-hash、任务定义和服务资产归属清单。准备受限目录、凭证和服务，确认 ready／协议／认证后，再原子发布三 hook 设置；最后确认登录任务与安装 manifest 已持久化。任一中间步骤失败按日志补偿，不留下“配置已指向不存在的新服务”。undo 同时恢复本工具改变的 ACL／任务属性；后来被他人改过的属性先报告冲突，不擅自覆盖，也不扩大仍含有效凭证的文件权限。
3. 全局 settings 变动影响该用户全部会话，不是只影响本 worktree；宿主何时重读 settings、老会话是否保留旧接线待测。默认先暂停其他会话的安装／升级操作，在约定窗口试装，不偷偷改变其他代理的运行入口。安装器之间串行化，对其他不协作的 settings 写者采用提交前再读 hash，发现竞争即中止。普通文件的“比较 hash 再 rename”不是原子 compare-and-swap，无法防住不协作写者恰在两者之间写入；必须有约定的无并发配置写入窗口，不能宣称已经解决任意外部编辑竞态。
4. 旧配置与新服务的兼容窗口显式登记并限时；新旧调用仍共用原回执语义。若宿主缓存旧 URL／token，无法仅靠改文件让它立即停止请求；提示需要重启相关会话，不把磁盘回滚等同于所有活会话已回滚。

### 7.3 一步撤销的顺序与保守失败

用户只发起一次 undo；该入口内部执行预检、禁用重启源、撤接线、排空、停进程和回收资产，幂等可重跑。顺序如下：

1. 在安装锁下标记 retiring，停用本安装登录任务／重启计划，保存其定义以便恢复，避免刚停就被拉起。
2. 检查全局 settings。若当前字节 hash 等于本安装 post-hash，原子恢复 pre 字节，**逐字节相同**；若安装前没有文件，只在确认该文件仍完全属于本安装时移入回收站恢复“不存在”。若后来有人编辑，不能恢复整份旧文件吞掉新设置：只对唯一匹配且完整可证明归属的 hook 做保留其他字节的局部撤销；该分支不宣称整个文件等于旧备份。重排／身份修改导致不能安全定位则不写文件，保留恢复资料并报告冲突。
3. 停止接受新的正常召回、撤销 token 的记忆访问权限；已入场请求最多等待一个短期限（拟 1s）排空，超时回降级。通过私有控制通道确认实例 ID、用户、PID 与起始身份，准备停止但不先退出到无法处理下一步；失联时只在能证明进程归属时终止，不按端口号／进程名杀别人的 Node。
4. 接线已安全撤回时，作废 token，关闭监听与 worker，确认进程退出。若 settings 冲突尚未解开或活会话仍缓存旧 HTTP 接线，则在同一前端保留一个已登记、可见标识的临时降级响应器：释放 corpus／worker，旧凭证只允许得到固定一行告警，不得查询记忆；明确报告“卸载未完成”。只有已验证停止后宿主仍安全放行时，才可到明确期限自动停它；否则先要求重启相关会话，确认无旧调用后完成停机。不能既声称“全卸载成功”又让旧接线无声拒连，也不能为了满足一步命令而强行停掉未知失败语义下的活接线。
5. 把本安装的 token、运行描述、缓存、无正文日志、备份与独占程序目录通过 Windows 回收站 API（如 IFileOperation 的可回收选项）移入回收站，清单记录原位置与结果；不得使用 rm／unlink 作卸载清理。计划任务先导出定义到受限文件再取消登记，并把定义回收。原始记忆、用户 config、共享阶段 1 receipt/state、其他代理资产、当前工作树不动。

共享的服务／程序资产仍被其他登记安装代引用时保留，不抢停他人使用中的实例。回收站不可用、文件被占用、目录权限错误时，保持撤接线／停用的已完成步骤，遗留物留原处且受限，报告待重试；**不退化为永久删除**。恢复资料和事务记录应保留足够的信息以定位回收站项目，不能先清掉唯一 undo 入口再执行未完成的清理。

“一步”指一个入口可处理正常路径，不代表在他人并发编辑时可以无条件无损撤销；冲突必须显式失败。原 `recall-receipt` 正常运行的 7 天／128 文件清理仍是既有行为，不拿它当 daemon 卸载器，也不把其 unlink 行为描述成回收站清理。若要求所有既有运行时清理也禁止永久删除，那是独立范围变更，需要 Jax 决定。

## 8. 逐事件端到端延迟估算与测量办法

### 8.1 估算而非实测

前提：772 条量级、本地盘、服务和索引已预热、没有第三方慢 hook、实际命中与回执都开启。热路径粗预算：宿主调度／序列化／应用响应 25–70ms，loopback 与认证／IPC 3–10ms，源复核 3–12ms，选择／证明／渲染 8–30ms，回执和队列 10–35ms。各阶段有重叠和相关性；宿主开销完全待测，不能从这些区间反推必达。

| 事件／状态 | 现有基线 | 推荐自启 + 直连 HTTP 的端到端估计 | 验收说明 |
|---|---:|---:|---|
| SessionStart，ready | 本任务未给该事件基线 | 0.06–0.16s | 含 epoch／健康／按配置发送 Kernel，不只测 ping |
| UserPromptSubmit，ready | 0.76s | 0.06–0.16s | 含实际词法检索、最多三条和回执落盘 |
| PreToolUse 编辑（Edit／Write／MultiEdit），ready | 0.77–0.80s 范围内 | 0.07–0.18s | 包含 repo／路径证明，未知路径不能用空回包冒充成功样本 |
| PreToolUse Bash，ready | 0.77–0.80s 范围内 | 0.06–0.17s | 简单命令和不支持 shell 分开统计 |
| 源改变／预热中，前端可响应 | 无 | 0.04–0.12s 的降级回复 | 本次缺召回，单列失败／不可用率，不能计作性能成功 |
| 登录至完整 ready（非 hook 延迟） | 启动与装索引分项见第 1 节 | 约 0.5–1.2s | 安全扫描／冷盘可更慢；报告期间有多少请求降级 |
| HTTP 前端全死／超时 | 待测 | 取决于宿主连接／超时处理，目标不超过约 0.2s 的故障等待 | 不先给出“放行且可见”的虚假数字；宿主默认秒级 timeout 可能直接使方案失败 |
| 三事件 command 安全桥，服务 ready | spawn 下限约 0.3s | 0.30–0.48s | 安全退路，明确未达标；拒连可快速发现，仍付启动成本 |
| 按需启动的 SessionStart | 同上 | 约 0.30–0.55s，不等全量预热 | 若同步等待 ready 可能约 0.8–1.5s，不推荐；其余 ready 事件才可走 HTTP 快路径 |

推荐登录自启的理由之一就是不隐去 SessionStart 的成本。若 Jax 选择按需启动，须明确接受 SessionStart 的性能例外；未经同意不能擅自把“工程线 ≤0.2s”缩成只算 prompt。故障路径超时也单列，不通过无限等待来减少失败数。

内存暂按单代数十到数百 MiB 风险预留，不给未测 RSS 承诺；双代构建、MiniSearch 对象和 worker 固定成本须测。并发预计会拉高队列与盘延迟，不把单会话区间当作 20 会话保证。
